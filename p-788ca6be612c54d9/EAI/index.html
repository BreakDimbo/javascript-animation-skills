    核心结论

    企业级 Agentic AI 的价值应以可验收的业务任务衡量：在既定权限、风险和预算约束下，系统能否稳定完成符合质量门槛的任务，并将执行过程与成本记录到可追溯、可复现的程度。AgentOS（智能体操作系统）或 Token（词元）产量只是架构或运营输入，不构成业务价值证明。

    00 整体视图

    一张图看懂：能力从哪里来、在哪里运行、如何验收

    图中依次是四类供给（算力、模型服务、数据知识、Agent（智能体）构建），共享的运行与治理能力（AgentOS、Agent Harness（直译"智能体挽具"，指驱动模型执行任务的支架）、Agent Runtime（智能体运行时），职能可能重叠），连接工具与其他 Agent 的跨层协议（MCP（模型上下文协议）、A2A（智能体间协议）等），以及企业业务系统和可验收的业务产出。四类 Factory（工厂）是本研究的分析视图，不是行业统一分层。

    01 标准与治理

    哪些已成标准，哪些仍是提案

    企业级 Agentic AI 的标准化工作分散在基金会项目、社区提案、政府计划和厂商实现中，成熟度差异很大。引用一个概念前，应先确认它的类型、治理主体、版本状态和互操作范围；名称相似不代表已形成统一架构或采购类别。

    LF

    AAIF

    Linux Foundation（Linux 基金会）于 2025 年 12 月成立 Agentic AI Foundation（智能体 AI 基金会，简称 AAIF），创始贡献项目包括 MCP、goose 与 AGENTS.md。2026 年 10 月 22 日接纳 Agent Skills、Open Responses、OpenEnv、OpenSandbox，官方公告称项目已增至 10 个。

    10 个项目为：MCP（工具与资源连接，Anthropic）、A2A（Agent 间互操作，Google）、AGENTS.md（代码仓库约定，OpenAI）、goose（本地 Agent 实现，Block）、agentgateway（Agent 通信入口）、Agent Router（Agent 流量控制）、Agent Skills（技能封装，Anthropic）、Open Responses（模型 API（应用程序接口）互操作，OpenAI）、OpenEnv（训练与评测环境，Hugging Face）、OpenSandbox（安全执行沙箱，阿里巴巴）。[S04]

    其 Taxonomy & Landscape Workstream（分类体系与全景图工作组）的目标是统一术语并建立 CNCF（云原生计算基金会）风格的生态图景；截至核验期，CONTRIBUTING（贡献指南）仍以 Taxonomy（分类体系）为重点，Landscape（全景图）的正式贡献流程尚待接受。

    术语工作流 · 已确立 Landscape · 待定稿
    CNCF

    AI Native Landscape

    AI Native Landscape（AI 原生全景图）重构议题提出将工作负载区分为 AI Agents（AI 智能体）、Inference（推理）、Training（训练）、Data（数据），并以 AI Native Infrastructure（AI 原生基础设施）作为共享基础。

    社区同时研究 Agent 互操作、编排、工具使用与可观测性；Agentic Standards Checklist（智能体标准检查清单）强调 Agent 身份、云原生部署与全生命周期治理。这些材料提供基线，但并未规定企业必须购入专有 AgentOS。

    提议结构 · 未生效
    NIST

    AI Agent Standards Initiative

    美国国家标准与技术研究院（NIST）于 2026 年 2 月宣布的 AI Agent Standards Initiative（AI 智能体标准计划），将互操作、开放协议、安全身份作为工作方向。

    这是标准推进计划，而不是一套已经覆盖全部 Agent 运行与商业架构的规范。需特别注意「以用户名义行动」引出的授权与审计问题。

    推进计划
    证据规则证据排序为：原始标准/规范及治理状态 → 原始论文与源码 → 官方技术文档与版本记录 → 官方发布或营销资料 → 可追溯的第三方研究。对「首创」类断言额外要求排除更早的同义用法；对「生产级」断言区分功能存在、正式发布、可用地域、服务承诺与实际用户效果。

      02 企业参考架构

      八大能力域：各管什么、有哪些产品、常见误区

      各部分相互依赖，难以画成严格分层，因此本研究按「能力域」划分：C1–C8 八个能力域，加上安全治理（G1）与评测运营（G2）两条贯穿全部能力域的横轴。每个能力域列出职责、代表产品和最常见的误区。C1–C8、G1–G2 是本研究的分析坐标，不是官方标准。

      G1 · Security / Identity / Policy / Audit（安全 / 身份 / 策略 / 审计） 身份、权限、资源、注册、审计贯穿所有组件；高风险操作还需人工审批、停止与回滚机制。应在项目初期按风险等级配置基础控制，并在业务扩展时加深，而非到「高级阶段」才考虑安全。
      G2 · Evaluation / Observability / AgentOps / FinOps（评测 / 可观测性 / 智能体运维 / 成本运营） 评测、可观测、可靠性（恢复、SLO（服务等级目标）、告警）与成本治理同样横切。看得见调用不等于能证明结果正确；能算清 Token 也不等于能算清任务。

      四类工厂：供给什么、谁买单、怎么衡量

      「AI Factory」「Token Factory（Token 工厂）」等是厂商与行业常用的产业叙事。以下按供给内容、核心能力、评价指标、典型购买者和代表产品分别说明，并用「边界」注明它不是什么。

      04 协作架构

      从能力供给到业务任务：谁负责什么，如何验收

      企业可以在多个系统间共享身份、策略、沙箱、状态、观测和审计能力，不一定需要一个名为 AgentOS 的独立产品。Agent Harness 负责执行循环和工具调用，Agent Runtime 负责任务托管与隔离；MCP、A2A、OpenAPI（开放接口描述规范）或事件接口的验收，须连同业务权限和事务语义一起进行。

      四厂之间的供给关系

      AI → Token
      算力供给：集群、加速器与推理底座。
      Token → Knowledge
      Embedding（向量嵌入）、抽取与分类所需的模型服务。
      Knowledge → Agent
      检索与数据；场景反馈回流知识层。
      Token → Agent
      模型路由、预算与成本归因。

      共享某项能力不等于包含另一个工厂；调用外部 API 也不等于拥有底层工厂。

      可共享的运行与治理能力

      运行与治理
      身份与权限、资源调度、沙箱隔离、记忆与状态、审计合规、多智能体管理；可由多个现有系统组合实现。
      跨层协议
      MCP 连接工具与资源；A2A 支持多智能体协作；OpenTelemetry（开放遥测标准）贯通可观测性。

      价值口径

      更高的任务完成率
      从演示走向稳定业务产出的比例。
      更低的单位任务成本
      Token + 运维 + 重试 + 人工的综合成本。
      更高的业务 ROI
      降本、增收、新业务三类收益可分别归因。

      06 概念辨析

      最常被混用的四组概念

      这四组名称经常在产品文档和方案讨论中混用。判断时应看运行对象、接口、责任边界、管理平面和故障语义，而不是产品名称。

      Framework≠Harness

      Framework（框架）是用于构建 Agent 的可编程积木；Harness 是把模型置于目标、上下文、工具、反馈、验证和停止规则中的可执行支架。两者可以重叠。

      OpenAI 2026 年 Agents API 以托管 Codex Harness 为核心，说明 Harness 也能由远端托管服务交付；Microsoft Agent Framework 文档则把 Harness Agent 作为框架内一种特定 Agent 实现。

      Claude Agent SDKOpenAI CodexMicrosoft Agent Framework

      Agent Runtime≠Model Runtime

      Agent Runtime 运行 Agent 应用与任务控制逻辑；Model Runtime（模型运行时）托管模型权重、批处理和 Token 生成。Google 官方参考架构明确区分这两个运行时。

      Red Hat AI Inference / vLLM / llm-d 主要属于模型推理及其分布式调度领域，而 AWS AgentCore Runtime 主要面向 Agent 执行环境。

      AgentCore RuntimevLLMllm-d

      Control Plane≠AgentOS

      控制平面是管理身份、注册、策略和生命周期的一组系统职责；AgentOS 仍缺乏统一行业规范，可以是多种能力的组合与商业命名。

      Microsoft Agent 365 和 IBM watsonx Orchestrate 均有官方控制平面定位，但商业边界并不完全相同。同名不等于跨厂商能力相同。

      Microsoft Agent 365IBM watsonx Orchestrate

      MCP≠A2A

      MCP 的核心是 AI 应用与工具/资源的标准化连接；A2A 的核心是独立 Agent 的能力发现与任务协作。二者可共存，也不排斥 REST（表述性状态转移）接口、队列与企业事件总线。

      MCP 不提供自动授权，A2A 也不证明远端 Agent 的行为值得信任。

      MCPA2AREST / 事件总线

      08 选型与建设

      先问业务需要哪些能力，再看平台

      比较产品时，应逐项记录主营类别、支持能力、开源或商用形态、运行边界、部署模式、扩展接口、已验证版本、成熟度和主要约束。一格一产品的 Landscape 图适合了解概况，不能作为采购比选依据。

      场景 A · 单任务、低风险、有限并发

      典型：查询、抽取、单据生成、内部问答
      • 优先成熟业务接口、最简单的工作流与少量工具调用。
      • 只有当固定流程无法覆盖业务变化，才引入自主 Agent。
      • 把复杂度预算留给后面，而不是一开始就上多 Agent。

      场景 B · 跨系统、高权限、长时间执行

      典型：订单到收款、对账、运维处置、合规审查
      • 优先定义业务对象、授权/委托、可逆事务、沙箱、持久化恢复、追踪与人工接管。
      • 挑选 Runtime 与 Control Plane，而不是先讨论叫不叫 AgentOS。
      • Durable（持久化执行）要测副作用重放，不能只凭「支持会话」宣称。

      场景 C · 多团队、多厂商、多 Agent

      典型：集团级平台、跨部门智能体资产
      • 优先统一目录、身份、工具策略、接入规范、成本与质量口径，再评估跨平台控制平面。
      • 对过早创建统一平台的方案，要计算持续适配与治理开销。
      • 「一个控制平面治理所有 Agent」是带条件的主张。

      Build vs Buy：什么该自建

      当企业需要差异化业务决策逻辑、复杂本地系统对接、可审计的自有知识模型、关键工作流规则时，应考虑自建上层业务适配与 Agent 逻辑。

      通用模型 Serving、日志、身份、Agent Registry（智能体注册中心）或沙箱，则可在安全、交付模式和 TCO（总拥有成本）允许时采购或复用。

      关键判断全自建并不是「自主可控」的唯一解；标准接口、可导出的数据与工件、明确的切换预案，往往更有效。

      同一产品往往横跨多个能力域

      Google ADK 首要属于 Framework，但能实现编排与多 Agent 协作；AWS AgentCore 是可组合的托管服务集合，其 Runtime、Memory、Gateway、Browser（浏览器）、Code Interpreter（代码解释器）、Identity（身份）在功能上分别跨越不同域。

      因此，厂商架构要做保真映射而不是强行归层；「成熟度和可用区须在项目部署前重新核验」。

      建议指标 / 本研究口径，非官方标准

      每项成功任务完全成本 =（模型和推理 + 工具调用 + Agent 运行 + 数据知识维护 + 人工复核 + 失败重试 + 安全合规 + 运维资源 + 故障和回滚成本）
      ÷ 满足质量门槛的任务数

      指标须定义任务分母、成功标准、异常处理和分摊边界，并区分一次性建设费用与持续运营成本。相同模型、不同 Harness、工具和知识质量会显著改变业务成功率，因此不能只根据百万 Token 单价决定选型。
